ĐỀ CƯƠNG NGHIÊN CỨU & PHÁT TRIỂN
ORCHEST COMPUTING
Runtime Orchestrator Cho Suy Luận Mô Hình Ngôn Ngữ Lớn Phân Tán
Trên Cụm Thiết Bị Biên Dị Chủng Windows CUDA – macOS MPS
(Prefill/Decode & KV-Cache-Aware Cost Model with Rigorous Regret Evaluation)
TÓM TẮT ĐỀ TÀI (ABSTRACT)
Nghiên cứu này thiết kế và hiện thực Orchest Computing — một runtime orchestrator phục vụ suy luận mô hình ngôn ngữ lớn (LLMs) theo mô hình song song đường ống (Pipeline Parallelism) trên cụm thiết bị cá nhân dị chủng (Windows CUDA và macOS Apple Silicon) qua mạng cục bộ (LAN). Thay vì dàn trải vào các tính năng đã tồn tại trong các công trình đi trước (như auto-discovery hay topology placement chung chung), Orchest tập trung định vị đóng góp mới vào: (1) Xây dựng Cost Model phân tách hai pha Prefill (Compute-bound) và Decode (Bandwidth/Memory-bound), tích hợp ràng buộc bộ nhớ động (KV-cache footprint theo context length & batch size) và mức độ đồng thời (concurrency); (2) Thuật toán quy hoạch động (DP) tối ưu hóa phân rã layer liền kề (Contiguous Layer Partitioning) trên cụm Windows–macOS dưới ràng buộc Working Set bộ nhớ khả dụng của accelerator; và (3) Đánh giá thực nghiệm chuẩn mực cao với sai số dự báo (Prediction Error - MAPE/RMSE) và độ hối tiếc phân hoạch thực tế (Realized Partition Regret) so với Measured Oracle.
MVP trong 18 tuần tập trung trên nền tảng runtime đồng nhất PyTorch (CUDA trên Windows và MPS trên macOS); MLX adapter được quy hoạch là mục tiêu mở rộng cho giai đoạn ĐATN.
1. TỔNG QUAN NGHIÊN CỨU & MA TRẬN SO SÁNH (RELATED-WORK MATRIX)
Các công trình như PipeEdge, exo, Petals và PyTorch Pipeline Parallelism (PiPPy) đã chứng minh tính khả thi của việc suy luận phân tán trên edge. Tuy nhiên, việc đánh giá toàn diện các hệ thống hiện hữu cho thấy vẫn tồn tại những khoảng trống nghiên cứu rõ rệt, đặc biệt là việc tối ưu hóa nhận thức KV-cache, chi phí mạng hai pha riêng biệt, và đánh giá độ tin cậy của Cost Model:
2. ĐỊNH VỊ ĐÓNG GÓP MỚI (NOVEL CONTRIBUTIONS)
1. Prefill/Decode- & KV-Cache-Aware Cost Model: Xây dựng mô hình chi phí toán học phân tách rõ ràng hai giai đoạn: Prefill (Compute-bound) phụ thuộc TFLOPs và prompt length; Decode (Bandwidth-bound & Memory-bound) phụ thuộc Memory Bandwidth và Inter-token transfer size. Tích hợp động dung lượng KV-cache headroom theo ngữ cảnh tối đa và mức tải đồng thời.
2. Contiguous Layer Dynamic Programming Partitioning: Thiết lập bài toán tối ưu hóa phân hoạch chuỗi L layer liền kề trên cụm K nodes bằng thuật toán Quy hoạch động (DP) với độ phức tạp O(K * L^2), đảm bảo thỏa mãn ngưỡng an toàn 90% bộ nhớ khả dụng của accelerator.
3. Đo lường Sai số dự báo & Partition Regret: Đánh giá định lượng chất lượng của Cost Model thông qua sai số dự báo thời gian từng stage (MAPE, RMSE) và độ hối tiếc phân hoạch (Realized Partition Regret = TTFT_DP - TTFT_Oracle) so với lời giải vét cạn thực tế trên cụm vật lý.
3. MÔ HÌNH TOÁN HỌC & ĐỊNH NGHĨA WORKING SET
3.1. Định nghĩa chuẩn về Model Working Set (Giải quyết RQ1 & RQ3)
Thay vì sử dụng tiêu chí định tính 'mô hình lớn hơn VRAM của từng node', đề tài chuẩn hóa định nghĩa Model Working Set M_working cho phân đoạn layer [i..j] trên node k như sau:

    M_working(k, i, j) = M_weights(i, j) + M_peak_act(i, j, S_prefill, B) + M_KV-cache(i, j, S_max, B) + M_runtime_reserve(k)

Trong đó:
• M_weights(i, j): Dung lượng trọng số của các layer [i..j] theo kiểu dữ liệu (dtype_bytes).
• M_KV-cache(i, j, S_max, B) = 2 * 2 * (j - i + 1) * n_heads * d_head * S_max * B * dtype_bytes.
• M_peak_act: Bộ đệm tensor kích hoạt cực đại trong pha Prefill.
• M_runtime_reserve(k): Bộ nhớ dành riêng cho PyTorch runtime context (CUDA context / MPS framework overhead).

Điều kiện khả thi của phân hoạch:
1. Trên từng node k: M_working(k, i, j) <= Memory_usable(k) * 0.90 (với Memory_usable là VRAM trên Windows CUDA hoặc Unified Memory khả dụng trên macOS).
2. Toàn cụm: Tổng Memory_usable >= M_working(1, L), trong khi max_k(Memory_usable(k)) < M_working(1, L).
3.2. Thuật toán Quy hoạch động (Dynamic Programming)
Với chuỗi L layers và cụm K nodes có thứ tự cố định, công thức truy hồi tìm điểm cắt tối ưu giảm thiểu TTFT:

    DP[k][j] = min_{0 <= i < j} { DP[k-1][i] + C_pre(k, i+1, j) }

    với C_pre(k, i+1, j) = T_compute_pre(k, i+1, j) + T_comm(k-1, k, ActivationSize(i))

Nếu M_working(k, i+1, j) vượt quá ngưỡng an toàn bộ nhớ của node k, gán C_pre = infinity.
4. PHẠM VI CÔNG NGHỆ (MVP SCOPE & BACKEND STRATEGY)
• MVP Khả thi (18 tuần): Khóa cứng trên nền tảng runtime đồng nhất PyTorch. Trên Windows sử dụng backend PyTorch CUDA kết hợp NVML/WMI; trên macOS sử dụng backend PyTorch MPS (Metal Performance Shaders) kết hợp macOS native system APIs. Điều này đảm bảo tính nhất quán về memory tensor layout, serialization (torch.Tensor) và code path phân rã layer (AutoModelSlicer).
• Giai đoạn ĐATN (Future Work): Xây dựng MLX Adapter độc lập. Do MLX là một framework độc lập với runtime và tensor format riêng (không phải PyTorch device backend), việc tích hợp MLX song song cùng lúc với PyTorch CUDA/MPS sẽ phân mảnh mã nguồn và vượt quá quỹ thời gian 18 tuần.
5. KIẾN TRÚC AN NINH & CƠ CHẾ CHỊU LỖI
1. mTLS & ZeroMQ Curve Security: Xác thực hai chiều (Mutual Authentication) qua chứng chỉ số X.509 (ca.crt, host.crt, worker.crt) và mã hóa kênh truyền gRPC / ZeroMQ Curve.
2. Toàn vẹn gói tin (CRC32 Integrity): Checksum CRC32 4-byte đính kèm header cấu trúc cố định (HEADER_STRUCT = '!4sHIII'). Discard gói tin ngay tại tầng transport nếu có sai lệch.
3. Allowlist kiểm soát Node: Bộ lọc allowlist tại HostOrchestrator ngăn chặn worker lạ phát beacon UDP tham gia vào cụm.
4. Xử lý lỗi cấp Session (Safe Failure): Áp dụng Safe Failure: Khi worker gặp sự cố, hủy request hiện tại an toàn, re-profile cụm, kích hoạt DP tính toán lại phân hoạch trên các node khả dụng và phục vụ session tiếp theo (không dùng live migration phức tạp).
6. THIẾT KẾ BENCHMARK (5 SUB-STUDIES)
Để tránh bùng nổ không gian thực nghiệm (full Cartesian product), bộ benchmark được cấu trúc thành 5 nghiên cứu tập trung:
1. Core Matrix Study: Đánh giá TTFT, Inter-token Latency (ITL), Throughput trên các model chuẩn (Qwen-2.5-0.5B, 1.5B, 3B, 7B) so sánh giữa DP, Heuristics (Equal, Mem-prop, Compute-aware) và Single-node Baseline.
2. Network Impact Study: Đo lường độ nhạy cảm của pipeline khi thay đổi RTT (0.5ms -> 20ms) và Bandwidth (100 Mbps -> 1 Gbps) trên kết nối Wi-Fi/LAN thực tế.
3. Concurrency & KV-Cache Study: Khảo sát hành vi của Cost Model khi tăng S_prompt (128 -> 2048), S_gen (64 -> 512) và Batch Size (B = 1, 2, 4).
4. Security Ablation Study: Đo lường chính xác Overhead (latency & throughput degradation) của mTLS + CRC32 so với Raw TCP không mã hóa.
5. Thermal & Stability Study: Đo lường hiện tượng suy giảm hiệu năng do quá nhiệt (Thermal Throttling) trên laptop Windows và MacBook (Fanless vs Active Cooling) khi chạy suy luận liên tục.
Quy chuẩn Single-Node Baseline & Heuristics
• Single-Node Baseline: Đo trên node mạnh nhất trong cụm, giữ nguyên: weights, dtype (FP16), quantization, tokenizer, sampling parameters và caching strategy. Nếu model vượt quá VRAM của node này, kích hoạt baseline CPU / Unified Memory Offloading.
• Heuristics Baselines: Equal-layer, Memory-proportional, Compute-aware đều phải chạy dưới cùng Fixed Node Ordering và áp dụng cùng Hard Memory Constraint.
7. GIAO THỨC ĐO LƯỜNG & TIÊU CHUẨN THỐNG KÊ (RIGOROUS PROTOCOL)
• Độ tin cậy thống kê: 5 - 10 independent runs; mỗi run thực hiện hàng trăm (hundreds) request observations. Báo cáo Median, p95 Latency và Bootstrap 95% Confidence Interval (CI).
• Kiểm soát điều kiện biên: Ngẫu nhiên hóa thứ tự thử nghiệm giữa các phương pháp; nghỉ cool-down 60s giữa các block đo để tránh tích tụ nhiệt; cố định driver, OS build, model hash và cấp nguồn AC.
• Numerical Correctness Criteria: So sánh với Single-node Eager PyTorch. Tiêu chuẩn: Logit Relative Error <= 1e-3, Cosine Similarity >= 0.9999, Directional KL Divergence <= 1e-4, Greedy Token Agreement = 100% trên 100 prompts cố định.
• Cost Model & Regret Metrics: Tính MAPE/RMSE giữa thời gian dự báo và thực tế; Spearman rank correlation; và Realized Regret = TTFT_DP - TTFT_Oracle.
